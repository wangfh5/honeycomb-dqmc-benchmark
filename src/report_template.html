DQMC performance report: Honeycomb Hubbard model

INITIAL STATE

Timing comparison of auxiliary-field update algorithms for projector determinant quantum Monte Carlo (DQMC) on the honeycomb Hubbard model.

  • Delay-T, delay-G, submatrix-T, and submatrix-G are timed at their optimal delay-block size nd.
  • Each delayed-update size has at least five independent fixed-seed runs. Fast update has one completed timing run through L = 60.
  • Filled symbols are measurements; error bars are the observed min–max across compute nodes.
  • Open symbols and dashed extensions show Fast update and sweep-time estimates at L = 66 and 72.

The delayed-update algorithms follow Fo-Hong Wang, Fanjie Sun, Cheng-Hao He, and Xiao Yan Xu, Resolving Quantum Criticality in the Honeycomb Hubbard Model, arXiv:2602.03656.

GitHub repository: wangfh5/honeycomb-dqmc-benchmark

What is timed
  • Sweep time is the cost of one Monte Carlo sweep of the space-time lattice.
  • Stage shares use the same sweep clock: auxiliary-field update, imaginary-time propagation, numerical stabilization, and measurement.
  • They exclude the one-time sweep-start setup where the numerical-stabilization matrices and the Green's function are initialized from a random auxiliary-field configuration and the trial wave function.
  • The program wall time also includes that initialization and final I/O.

Update time vs size

  • Cost of the auxiliary-field update within one sweep.
  • Symbols: median; bars: observed min–max.
  • Hover for sample count and optimal nd.
  • Fast L = 66 and 72 are estimated by subtracting the same-size Submatrix-T median non-update time from the Fast sweep estimate.

Sweep time vs size

  • Same runs as the update-time panel.
  • Includes update, propagation, stabilization, measurement, and remainder I/O inside the sweep.
  • Excludes that one-time sweep-start setup of the stabilization matrices and the Green's function.
  • Fast L = 66 completed, but its detailed TIMING output is unavailable; the plotted sweep time is inferred from the completed-job wall time.
  • Fast L = 72 is extrapolated from the stable per-slice sweep time observed over 15 days of runtime.

Speedup relative to Submatrix-T

  • Vertical axis is comparator / submatrix-T.
  • Values above 1× mean submatrix-T is faster.
  • Fast L = 66 and 72 are estimates for both metrics and are drawn with open symbols and dashed extensions.

Optimal delay-block size nd vs size

  • Delay-block size nd chosen by the lowest median sweep time.
  • Shown only for the four delayed-update algorithms.
  • Background colors mark the 1 / 4 / 16 / 32 OpenMP-thread resource bands.

Hardware utilization

  • Delayed-update points: one scan winner plus four independent repeats at the optimal nd.
  • Fast update: one completed timing run per size.
  • Centers are medians; bars are min–max. A single run has no error bar.

Stage time shares

  • Each bar is one sweep, normalized to 100%.
  • Turn on Split update to draw other operations versus update of T or G.
  • Hover a bar for the same breakdown.
  • Error bars are the observed range over independent runs, not fit uncertainties.
  • CPU efficiency is DQMC process CPU time divided by allocated core-hours.
  • Memory efficiency is peak resident memory divided by allocated memory.
  • From L = 36 the allocation increases from 500 GiB to 1000 GiB, so the memory percentage also changes with the denominator.
  • For delayed updates, update time = other operations + update of T or G; both are drawn inside the update segment.
  • Fast update does not report that split.
